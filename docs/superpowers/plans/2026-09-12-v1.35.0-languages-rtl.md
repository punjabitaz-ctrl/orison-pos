# Languages and Right-to-Left (v1.35.0) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Run the whole till in English, Arabic or Urdu, laid out right-to-left where the language is, with the language offered on the login screen and in Settings.

**Architecture:** Every user-visible string goes through `t()` with the English text as its key. Arabic and Urdu catalogues are ES modules, so they are precached for offline use and loaded without a fetch. A test scans the source for every `t()` / `tn()` / `N_()` literal and fails the build if any language is missing one, so a half-translated screen cannot ship. The CSS moves to logical properties so layout mirrors under `dir="rtl"`.

**Tech Stack:** Vanilla ES modules, `Intl.PluralRules`, CSS logical properties, `node:test`.

## Owner decisions (2026-09-12)

- Right-to-left is in scope.
- Offer the language options.

## Decisions taken here

| Decision | Chosen | Why |
|---|---|---|
| Languages | **English, Arabic, Urdu** | Match the AED and PKR currencies the owner asked for; store setup already lists both. A fourth language is one catalogue file. |
| Keys | **The English text itself** | Retrofitting ~10k lines: no invented key names, English is its own fallback, code stays readable. |
| Plurals | **`Intl.PluralRules`** | Arabic has six plural forms (zero, one, two, few, many, other); a one/other scheme is simply wrong for it. |
| Missing translation | **Build fails** | A half-translated UI is worse than an English one. |
| Where the choice lives | **Terminal UI:** per-terminal (IndexedDB `meta/lang`), offered on login and in Settings, default "match the store". **Receipts and customer display:** the store's language. | The customer should not get the cashier's personal language. The store language already exists (v1.16.0) and is the admin's call. |
| Money and dates | **Unchanged: the store locale** | Formatting is a store setting; translation is a terminal setting. |
| Existing `public/js/i18n.js` | **Not used, not touched** | Untracked, not written in these sessions, unwired, and its `en.json` does not parse. It fetches JSON at runtime (invisible to the offline precache), knows only one/other plurals (wrong for Arabic), and silently falls back to English when a bundle fails. |
| Server error messages | **Translated in `api.js`**, for every fixed message | One place, since all server errors reach the screen through `api.js`. Messages built from numbers stay English. |

## Tasks

1. `public/js/lang.js` — `t`, `tn`, `N_`, `tIn`, `setLanguage`, `initLanguage`, `LANGUAGES`, `dirOf`; catalogues via literal dynamic imports. Unit-tested.
2. Extraction, screen by screen, into `t()` / `tn()` / `N_()`.
3. `tests/client-lang.mjs` completeness: every key in every catalogue; no unused entries; placeholders preserved; plural objects carry the forms the language needs.
4. `public/js/lang/ar.js`, `public/js/lang/ur.js`.
5. CSS: physical → logical properties; mirrored directional icons and slide-ins.
6. Language picker on login and in Settings; receipts and the customer display in the store language.
7. Browser pass over every screen in all three languages.
8. Release.

## Known limits, stated up front

- **The translations need a native speaker's review before go-live.** They are written carefully for a retail till, but no Arabic- or Urdu-speaking reviewer has checked them.
- Product names, customer names and anything typed into the system stay as typed.
- Server messages that embed numbers ("Only 3 of Cable left") stay English.
