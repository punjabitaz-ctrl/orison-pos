# Printing and the Cash Drawer (v1.34.0) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Print receipts to whatever printer the shop actually has — a receipt printer installed on the computer, an ordinary office printer, or a Bluetooth receipt printer — and open the cash drawer.

**Architecture:** One receipt model (`receipt-doc.js`) that every screen builds and every printer renders. Three output paths chosen per terminal in Settings: the system print dialog at roll width, a full page through the existing `print-sheet.js` window, or ESC/POS bytes over Web Bluetooth (`escpos.js` + `printer.js`). The drawer is kicked through the Bluetooth printer's drawer port.

**Tech Stack:** Vanilla ES modules, no build step. Web Bluetooth. `node:test` + `fake-indexeddb` for units.

## Owner decision (2026-09-12)

Support Bluetooth printers and standard computer printers, in addition to the receipt printer and cash drawer planned for v1.28.0. v1.28.0 is not reused: it would put a version number behind v1.33.0 and make the app's version go backwards.

## What the owners need to know before buying hardware

These are properties of browsers, not of this code, and they decide what works:

1. **Bluetooth printing needs Chrome or Edge** — on Windows, macOS, ChromeOS or Android. **It does not work on an iPhone or iPad** (Safari has no Web Bluetooth), and not in Firefox.
2. **The printer must support Bluetooth Low Energy (BLE).** Browsers cannot talk to "Bluetooth Classic"-only printers. Many cheap thermal printers are Classic-only; look for BLE or "Bluetooth 4.0+" in the spec, ideally one sold as working with web or Android apps.
3. **The cash drawer opens only through a directly connected receipt printer** — here, the Bluetooth one, with the drawer cable plugged into the printer's drawer (RJ11/RJ12) port. A browser cannot send the "open drawer" signal through the system print dialog. With a standard or dialog-driven printer, the drawer is opened with its key.

A USB receipt printer installed on the computer prints through option 1 (the print dialog) today, with no drawer kick.

## Decisions

| Decision | Chosen | Why |
|---|---|---|
| Setting scope | **Per terminal** (IndexedDB `meta` / `printer`) | A printer is a physical thing next to one till. |
| Bluetooth text vs image | **Plain text when the receipt is pure ASCII, otherwise a printed image (raster)** | ESC/POS text depends on the printer's code page, so `£ € ₨ د.إ` and Arabic/Urdu print as garbage. Rendering the receipt to a canvas and sending it as a raster prints any script and symbol on any ESC/POS printer. Text mode is kept for speed where it is safe. |
| Paper widths | 58 mm (384 dots, 32 cols) and 80 mm (576 dots, 48 cols) | The two roll sizes in practice, at 203 dpi. |
| Drawer pin | Pin 2 default, pin 5 selectable | Drawers are wired to one or the other. |
| Manual "Open drawer" | Manager/admin tile, **audited** | A no-sale drawer open is the classic till-theft move. The audit is best-effort online. |

## Tasks

1. `public/js/receipt-doc.js` — `receiptDoc(tx, ctx)` builds one model from a sale: header, meta, lines, totals (tax line only when there is tax; discount only when there is one), tenders with real labels (including **Deposit applied**), change, footer with receipt number or the pending-sync note. Unit-tested.
2. `public/js/escpos.js` — pure bytes: init, align, bold, text columns padded to width, feed, cut, `drawerKick(pin)`, `rasterImage(bits, w, h)` (`GS v 0`), `packBits(rgba, w, h)`, `chunk(bytes, size)`, `isPlainAscii(doc)`, `escposFromDoc(doc, cols)`. Unit-tested byte-for-byte.
3. `public/js/printer.js` — settings load/save with defaults; `bluetoothSupported()`; a Bluetooth transport that finds the first writable characteristic and writes in chunks; `printReceipt(doc)` dispatch; `openDrawer()`. Transport and renderers injectable, so it is unit-tested against a mocked `navigator.bluetooth`.
4. `public/js/receipt-render.js` — `rollHtml(doc)`, `sheetHtml(doc)`, `docToCanvas(doc, widthDots)`. Browser-verified.
5. Backend `POST /api/drawer/open` → audit `drawer.open` (manager/admin). Sim-tested.
6. UI: Settings **Printer & cash drawer** card; checkout Print (plus auto-print and kick-on-cash); History **Print receipt** reprint; Repairs print after collection; **Open Drawer** tile.
7. `_headers`: `bluetooth=(self)` in `Permissions-Policy`, explicitly.
8. Release v1.34.0.

## Verification limits, stated up front

- **No physical printer is available.** ESC/POS bytes are tested exactly, the Bluetooth transport is tested against a mock, and the dialog/page/canvas output is checked in a browser. The first real print on the shop's hardware is still the real test.
- `pdf-smoke` remains unrunnable here (Edge refuses headless).
