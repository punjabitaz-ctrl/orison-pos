# Repair Deposits and Collection (v1.32.0) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Take a deposit when a repair is booked in, and collect the job as a real sale — without a deposit ever counting as revenue, and without the same pound touching the drawer twice.

**Architecture:** Three server endpoints write ledger rows directly under the script lock, the way `purchaseOrderReceive_` already writes its `purchase` row. They do **not** go through `/api/sync/push`. Two new ledger kinds (`deposit`, `deposit_refund`) and one new tender type (`deposit`) are threaded through every place the codebase classifies money.

**Tech Stack:** Google Apps Script on Sheets; vanilla ES-module PWA; `tests/backend-sim.mjs`, `tests/client-*.mjs`.

## Global Constraints

- **Source of truth:** `docs/superpowers/specs/2026-09-12-repairs-design.md`, section *v1.32.0 — the money*.
- **The invariant:** cash touches the drawer exactly once per unit of currency. A deposit adds it; the `deposit` tender at collection does not add it again; a deposit refund removes it.
- **A deposit is never revenue.** It must not appear in gross sales, net revenue, gross profit, per-cashier sales, or the dashboard's "Net revenue today".
- Everything from the v1.31.0 plan's Global Constraints still holds (ES5 backend style, lock on every read-modify-write, `IN_STOCK`/`SOLD`/`VOIDED`, escape on render, never `&&`-chain gate→commit→tag).
- **Never `git add -A` in this repo** while the untracked `public/js/i18n.js` / `public/locales/` sit in the tree. Name files.

## Why collection cannot go through `/api/sync/push`

Found while mapping the code, and the single most important constraint here:

`syncPush_`'s sale path **decrements stock** for every line. v1.31.0 already took the parts off the shelf when they were fitted. Routing the collection sale through sync push would take every fitted part off the shelf a second time.

So collection writes the `sale` row itself, reusing `resolvedItems_`-shaped items and `reserveReceiptNumbers_`, and touches no stock.

## The four places a deposit would silently become revenue

Each of these was found by reading the code, and each gets a test:

| Where | The trap |
|---|---|
| `public/js/money.js` `kindInfo()` | Returns `map[kind] \|\| map.sale` — an unknown kind **displays as "Sale"** and prints as a sale receipt. |
| `public/js/stats.js` `signedNet()` | Everything that is not a refund or cash-out is `+`. The dashboard labels the sum **"Net revenue today"**, so a deposit — *and a deposit refund* — would show as revenue. |
| `backend/Code.gs` `driveExport_` | `else if (k !== 'purchase') sales += v;` — every unrecognised kind is **counted as sales** in the day export. |
| `backend/Code.gs` `syncPush_` | An unrecognised kind falls through to the sale path. And tender types are not validated, so a device could push a sale "paid" with a `deposit` tender — goods leave, nothing hits the drawer, and the report shows it as settled. |

`reports_` and `shiftClose_` branch explicitly on known kinds, so an unknown kind is merely *ignored* there — safe, but it means deposits would be missing from the drawer count. They get explicit branches.

`receivables_` only counts `account`/`net30`/`store_credit` tenders, so neither a deposit row nor a `deposit` tender can create a customer debt. No change needed; a test pins it.

### Task 1: Refuse forged deposits at the sync boundary

**Files:** `backend/Code.gs` (`syncPush_`), `tests/backend-sim.mjs`

- A pushed transaction with `kind` of `deposit` or `deposit_refund` is rejected with `reason: 'server_only_kind'`. These kinds are only ever written by the repair endpoints.
- A pushed sale carrying any tender with `type === 'deposit'` is rejected with `reason: 'deposit_tender_not_allowed'`.

Tests: both rejections return `accepted: false`; the rejected sale does not move stock.

### Task 2: Take a deposit

**Files:** `backend/Code.gs` (`repairDeposit_`, route `POST /api/repairs/deposit`), tests

- Any store role. Ticket must exist and not be terminal. `amount > 0`.
- Tenders default to `[{ type: 'cash', amount }]`. Allowed types: `cash`, `card`, `transfer`. Tender sum must equal `amount` to the cent.
- Writes one `Transactions` row: `kind: 'deposit'`, `grand_total: amount`, `counterparty: ticket_no`, `note: 'Deposit on ' + ticket_no`, `customer_id` from the ticket, `status: 'COMPLETED'`, `items_json: '[]'`. No receipt number (not a document kind).
- Ticket `deposit_total += amount`. Audit `repair.deposit`.

### Task 3: Collect the job

**Files:** `backend/Code.gs` (`repairCollect_`, route `POST /api/repairs/collect`), tests

- Any store role — it is a sale. Ticket must exist, be open, and carry at least one part or labour line.
- Items: each part becomes `{ productId, name, quantity, unitPrice, serialNumber, unitCost }` (cost captured at fitting). Each labour line becomes `{ productId: labour.productId || 'repair-labour', name, quantity: 1, unitPrice: amount, category: 'Repairs' }`.
- Totals via `saleTotals_` at the store tax rate. Parts are taxable per their product; ad-hoc labour is taxable.
- `depositApplied = min(deposit_total, total)`. If `deposit_total > total`, **refuse with 409** — the difference must be refunded first, so the ledger never holds a deposit larger than the job it paid for.
- Client tenders cover the balance and must sum to `total − depositApplied`. The server **appends** `{ type: 'deposit', amount: depositApplied }` itself; a client-supplied `deposit` tender is rejected.
- Writes the `sale` row with `receipt_no` from `reserveReceiptNumbers_(1)`, `channel: 'in_store'`, `external_ref: ticket_no`. **Moves no stock.**
- Each fitted serial's `tx_id` is re-pointed from `repair:<id>` to the invoice id, so a later refund of that line sees a consistent serial.
- Ticket → `status: 'collected'`, `final_total`, `invoice_tx_id`, `closed_at`, `deposit_total: 0`. Audit `repair.collected`.

Tests: stock unchanged by collection; receipt number assigned; deposit tender present with the right amount; balance tenders validated; over-deposit refused; collected ticket cannot be collected again.

### Task 4: Refund a deposit

**Files:** `backend/Code.gs` (`repairDepositRefund_`, route `POST /api/repairs/deposit-refund`), tests

- **Admin/manager only** — money out, matching refunds and payouts.
- Ticket must not be `collected`. `deposit_total > 0`. Amount defaults to the full held deposit; a partial amount must be `> 0` and `≤ deposit_total`. Reason required.
- Writes `kind: 'deposit_refund'`, cash tender by default. Ticket `deposit_total −= amount`. Audit `repair.deposit_refund`.
- **`repairVoid_` now refuses a ticket with a deposit held** — voiding would orphan the liability.

### Task 5: The drawer, the reports and the export

**Files:** `backend/Code.gs` (`shiftClose_`, `reports_`, `driveExport_`, `reportEmailBody_`, `REPORT_DENOM_LABELS`), tests

- `shiftClose_`: `deposit` adds its cash tenders; `deposit_refund` subtracts them. The collection sale already counts only `cash` tenders, so its `deposit` tender is excluded without a change.
- `reports_`: `summary.depositsIn`, `depositsApplied` (sum of `deposit` tenders on sales), `depositsRefunded` over the window; **`depositsHeld` is point-in-time**, `Σ deposit_total` across the `Repairs` sheet — a balance is not a windowed figure. Deposit kinds stay out of gross sales, GP and per-cashier sales. `byTender` shows the sale's `deposit` tender as **"Deposit applied"**. `byProduct`/`byCat` fall back to the item's own `name`/`category` when there is no product row, so labour reads "Repair labour" rather than "Item".
- `driveExport_`: deposit kinds excluded from `sales`; `CASH IN DRAWER` includes deposit cash in and deposit-refund cash out; new `DEPOSITS IN`, `DEPOSITS APPLIED`, `DEPOSITS REFUNDED` lines.
- `reportEmailBody_`: a `Deposits held` line.

Tests — the ones that matter:
- **A deposit never appears as revenue**: gross sales, net revenue and GP are unchanged by taking one.
- **Cash touches the drawer once**: float + deposit + cash balance at close, not + deposit twice.
- Deposits held rises on deposit, falls on collection and on refund, and reaches zero.
- The export does not count a deposit as sales.

### Task 6: Client kinds and the dashboard

**Files:** `public/js/money.js`, `public/js/stats.js`, `tests/client-money.mjs`, `tests/client-stats.mjs`

- `kindInfo`: `deposit` → "Repair deposit" (sign +1), `deposit_refund` → "Deposit refund" (sign −1).
- `signedNet`: returns **0** for both deposit kinds — "Net revenue today" is revenue.
- `dayTotals`: `deposits` and `depositRefunds` fields; neither touches `sales`, `tickets` or `net`.

### Task 7: The Repairs screen

**Files:** `public/js/screens/repairs.js`

- Detail shows deposit held. **Take deposit** (open tickets). **Collect & charge** (open tickets with lines): shows total, deposit applied, balance due, and a Cash/Card choice; on success, toasts the receipt number. **Refund deposit** for admin/manager when a deposit is held and the ticket is not collected.
- List rows show a deposit marker.

### Task 8: Release v1.32.0

Version bumps, CHANGELOG / RELEASE_NOTES / HANDOVER in lockstep, gates, commit → tag → verify tag → push as separate commands.

## Known limits, recorded rather than hidden

- **Refunding a repair invoice** goes through the normal refund screen. Part lines refund and restock; an ad-hoc labour line is rejected as `unknown_product`, because it has no product row. Repair refunds are a warranty/rework policy question and belong with warranty tracking.
- **"Net revenue today" already counts collections** (`payment` kind) as revenue. Money received against an earlier account sale is not new revenue, so that figure is overstated on days a customer pays down their account. Pre-existing, spotted while mapping deposits, deliberately not changed here.
